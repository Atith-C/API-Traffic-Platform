00 · Orientation

The 60-second pitch

It's a lightweight API gateway + developer portal, in the spirit of Kong / Tyk / Apigee. Organizations register their APIs, mint API keys, and route real traffic through a gateway that authenticates the key, enforces rate limits and quotas, forwards the request to the configured upstream, measures it, logs it, and emits telemetry. On top of that sits multi-tenant auth + RBAC, analytics dashboards, and audit logging.

The one design constraint that shaped everything: its request/audit telemetry is emitted through a versioned, decoupled event contract so a second product (an observability platform) can consume it later with zero schema changes.

▸ Say this first in an interview

"It's a modular monolith in async Python. The interesting parts aren't CRUD — they're the gateway data-plane (rate limiting with Redis Lua, quota enforcement, upstream proxying) and the transactional outbox that guarantees telemetry is never lost. Everything else is clean layering around those two."

01 · Structure

Architecture at a glance

It's a modular monolith: one deployable process, but with hard internal boundaries between layers. You get the operational simplicity of a monolith (one deploy, one DB transaction spanning a request, easy local dev) with the internal decoupling that lets you split a module into its own service later if you ever need to.

HTTP request
   │
   ▼
api/  (FastAPI routers — thin: parse → call one service → serialize)
   │
   ▼
services/  (business logic, orchestration, authorization decisions)
   │
   ▼
repositories/  (the ONLY layer that touches the ORM / DB session)
   │
   ▼
models/  (SQLAlchemy 2 ORM — UUID PKs, timestamps)

   side rails used by every layer:
   schemas/ Pydantic DTOs   core/ config · security · errors · redis · telemetry

Why async?

The platform is I/O-bound: nearly every request makes a DB round-trip plus a Redis round-trip, and the gateway path additionally makes an outbound HTTP call to an upstream. Async (FastAPI + SQLAlchemy 2 async + asyncpg + httpx) lets one worker handle many concurrent in-flight requests without a thread per request — exactly the concurrency profile a gateway needs. CPU work (password hashing) is the rare exception and is deliberately bounded.

The request lifecycle

  1. Request-context middleware assigns a request_id + correlation_id, binds them into the logging context (so every log line in that request is traceable), and logs a structured access line with latency on the way out.
  2. Routing → a router handler resolves its dependencies (session, current user, permission check) via FastAPI's DI.
  3. Handler calls one service method; the service uses repositories; the DB session commits at the end of the request (or rolls back on error).
  4. Any raised AppError is caught by a central handler and rendered as a consistent JSON error envelope; the X-Request-ID is echoed on every response.

◆ Interview Q

"Why a monolith and not microservices?"

Because the domain is small and highly cohesive, and a single process means a request's DB writes are one ACID transaction — which is what makes the transactional outbox trivial. Microservices would add network hops, distributed transactions, and ops overhead for no benefit at this size. The layering keeps the option open: services depend on repository interfaces, not on each other's internals, so a module could be extracted later.

02 · The golden rule

The layers & dependency injection

The single rule that keeps the codebase honest: business logic never lives in a route handler, and the ORM is never touched outside a repository.

LayerResponsibilityHard rule
api/Validate the request, call one service, serialize the result.No business logic. No DB access.
services/Business logic, orchestration, authorization decisions.Framework-agnostic — no FastAPI imports. Gets deps by constructor.
repositories/Data access for one aggregate; enforce tenant scoping.Only place that imports the session/ORM.
schemas/Pydantic request/response DTOs.Never expose an ORM object directly.
core/Config, security, errors, logging, redis, telemetry emitter.No feature logic.

Wiring happens at the edge. FastAPI's Depends() assembles a service from repositories + a session; inside the service everything is plain constructor injection. That's why services are unit-testable with fake repositories and know nothing about HTTP.

# api/deps.py — the composition root
def get_auth_service(session: SessionDep, sender: EmailSenderDep) -> AuthService:
    return AuthService(
        users=UserRepository(session),
        refresh_tokens=RefreshTokenRepository(session),
        email_sender=sender,
    )

◆ Interview Q

"How do you keep business logic testable?"

Services take their dependencies through the constructor and depend on repository classes, not on FastAPI. In a unit test I can pass an in-memory fake; in an integration test I pass a real repository backed by a Testcontainers Postgres. The service code is identical either way.

03 · The schema

Data model

Every table has a UUID primary key and created_at/updated_at timestamps (a shared mixin). A stable constraint-naming convention makes Alembic diffs deterministic. The entity groups:

  • Identity: users, refresh_tokens
  • Tenancy & RBAC: organizations, organization_members, roles, permissions, role_permissions
  • API catalog: apis, api_versions (each holds an upstream_base_url), quotas, rate_limit_rules, api_keys
  • Telemetry & analytics: request_logs, api_key_usage, audit_logs, telemetry_outbox, daily_usage
  • Misc: notifications

▸ Why UUIDs, not auto-increment ints

Two reasons that matter for this product: IDs are exposed in URLs/API responses, and sequential ints leak volume and are guessable (enumeration). UUIDs are non-enumerable and can be generated client-side / across shards without coordination. The trade-off — slightly larger index, non-sequential inserts — is negligible here.

Telemetry tables are deliberately decoupled from the transactional catalog tables (they reference IDs but avoid FKs into hot tables), carry composite (scope, created_at) indexes for time-range queries, and are designed to be partitioned later. That decoupling is what lets the observability product ingest them without touching the write path.

04 · Security

Auth & tokens

Password hashing

Argon2id (via argon2-cffi) — memory-hard, the current OWASP recommendation, resistant to GPU cracking. On login, if the stored hash used outdated parameters we transparently re-hash (parameter upgrade). On a missing user we still run a hash to blunt timing side-channels.

Access vs refresh tokens

Access tokenRefresh token
FormSigned JWT (HS256)Opaque random string (token_urlsafe(48))
LifetimeShort (~15 min)Long (~14 days)
Stored server-side?No — stateless, verified by signatureYes — only its SHA-256 hash
Sent asAuthorization: BearerhttpOnly cookie + body

Access tokens are stateless so the common path (every API call) needs no DB lookup — just a signature check. Refresh tokens are opaque and stored hashed so a database leak can't be replayed, and so we can revoke them (you can't revoke a stateless JWT).

Refresh rotation with reuse detection — the crown jewel

Every refresh token belongs to a family (a family_id). Using a refresh token rotates it: the old one is revoked and a successor is issued in the same family. The security property comes from what happens on misuse:

normal:   R1 ──rotate──▶ R2 ──rotate──▶ R3        (each old token revoked)

stolen:   attacker replays R1 (already revoked)
          └─▶ reuse detected → revoke the ENTIRE family
              → R2, R3 die too → real user is forced to re-login

If a revoked token is ever presented again, that's proof of theft (either the attacker or the victim is replaying an old token). We can't tell which, so we revoke the whole family and force re-authentication. This is the standard OWASP refresh-token-rotation mitigation.

Email verification & password reset

Both use short-lived signed action tokens (JWTs with a purpose claim). A reset token is bound to a fingerprint of the current password hash, so it's effectively single-use — once the password changes, the fingerprint no longer matches and the link is dead. Email delivery sits behind an EmailSender interface (console impl now; swap for SES/SendGrid later).

Brute-force throttle

Login and reset endpoints run through a fixed-window Redis counter keyed by IP + email; over the limit returns 429 with Retry-After. It's deliberately separate from the gateway's configurable rate limiter — auth throttling is a fixed security policy, not a per-customer product feature.

◆ Interview Q

"Why not just use long-lived JWTs and skip the refresh dance?"

Because you can't revoke a stateless JWT before it expires. If a long-lived token leaks, the attacker has access until expiry. Short access tokens shrink that window to minutes; the refresh token — stored hashed and revocable, with rotation + reuse detection — gives you both good UX (you're not re-logging-in every 15 min) and the ability to cut off a stolen session immediately.

◆ Interview Q

"Why store the refresh token hashed instead of encrypted?"

We never need to read it back — we only need to recognize it when presented. A one-way hash is the right primitive for that: a DB leak yields hashes an attacker can't reverse into usable tokens. Encryption would imply a key we'd have to protect and rotate, for no functional gain.

05 · Authorization

RBAC & multi-tenancy

A user belongs to many organizations; in each they hold exactly one role (owner / admin / developer / viewer). Roles map to permissions like api:create, key:revoke, member:invite, analytics:read.

Single source of truth

The permission catalog and the role→permission mapping live in one Python module (core/permissions.py). It's seeded into the DB (roles/permissions/role_permissions) idempotently on startup for auditability — but authorization checks use the in-memory mapping for speed. A test asserts the two never drift.

How a check happens

require_permission(perm) is a dependency factory. It reads the {org_id} from the URL path, looks up the caller's membership in that org, and verifies their role grants the permission — returning the membership object for the handler to use.

# The route declares intent; the dependency enforces it.
@router.delete("/organizations/{org_id}/apis/{api_id}")
async def delete_api(api_id, service, _=Depends(require_permission(Permission.API_DELETE))):
    ...

Tenant scoping is enforced in the repository, not just the route. Every catalog query filters by organization_id, and mutating operations re-verify the resource belongs to the org in the path. So even with a valid ID from another tenant, you get a 404 — cross-tenant access is structurally impossible, not just checked at the door.

Invariants live in the service

Example: you can't demote or remove the last owner of an org. That rule is enforced in OrganizationService, so it holds no matter which route calls it.

◆ Interview Q

"Where do you enforce that tenant A can't read tenant B's data?"

Two layers. The require_permission dependency checks the caller is a member of the org in the path. But the real guarantee is in the repository: queries are scoped by organization_id, so a resource ID that belongs to another org simply isn't found. Defense in depth — a route bug can't leak data because the data layer won't return it.

◆ Interview Q

"Why keep the permission mapping in code if it's also in the DB?"

Checks need to be fast and can't afford a join per request, so the hot path reads an in-memory frozenset. The DB copy exists for auditability and so an admin UI could show/edit it later. A startup seed reconciles the DB to the code, and a unit test asserts they match — so there's exactly one source of truth with a fast cache in front of it.

06 · Credentials

API keys

Keys authenticate consumers at the gateway (distinct from user JWTs, which authenticate humans in the portal). Format: atp_<public-id>_<secret>.

  • Shown once. On creation we return the full key exactly once; we persist only its SHA-256 hash (unique-indexed for O(1) lookup), plus a public prefix and last-four for display.
  • Revoke is immediate (sets revoked_at).
  • Rotate issues a successor and grace-windows the old key (it keeps working for N hours, then expires) — so clients can roll over without downtime. Grace 0 = revoke immediately.

▸ Why a fast hash (SHA-256) for keys but Argon2 for passwords?

Different threat models. A password is low-entropy and human-chosen, so it needs a slow hash to resist brute force. An API key is high-entropy random (256 bits) — brute-forcing it is infeasible regardless — so we want a fast deterministic hash we can look up on every single gateway request without adding latency.

◆ Interview Q

"A customer says they lost their key. What can you show them?"

Only the prefix and last four characters — we never stored the secret, just its hash. They rotate to get a new one. That "we literally cannot recover it" property is the point: a DB compromise yields no usable keys.

07 · The data plane

The gateway — the heart of the product

This is the part that makes it a gateway and not a CRUD app. One catch-all route, /gw/{api}/{version}/{path}, accepts any method and runs the full pipeline:

1. Authenticate   hash the presented API key → look up → valid? not revoked/expired? API active?
2. Resolve        the key's API must match {api}; find active {version} → its upstream_base_url
3. Rate limit     per (api, key) via the configured strategy (Redis)   → 429 if exceeded
4. Quota          per key per period (daily/monthly, Redis)             → 429 if exceeded
5. Forward        httpx call to upstream: method, filtered headers, query, body
6. Measure        wall-clock latency, request/response byte sizes, status
7. Record         request_log + api_key_usage + telemetry event (one DB transaction)
8. Return         upstream's response verbatim (status, safe headers, body) + X-Gateway-Latency-Ms

Details that matter

  • Header hygiene: hop-by-hop headers (RFC 7230) and the platform's own auth headers (Authorization, X-API-Key) are stripped before forwarding — we terminate auth here, the upstream never sees the consumer's key.
  • Status passthrough: a real upstream 503 is returned as 503 — we don't mask the upstream's own status. Only when we can't reach the upstream (timeout, connection error) do we synthesize a 502.
  • Framework-agnostic core: the route hands the service plain primitives (method, path, headers, body), not a FastAPI Request — so the gateway logic is unit-testable and reusable.
  • Real upstreams: the upstream URL is per-version config, not a bundled fake. Demos point at httpbin.org; tests mock the outbound httpx client with respx so CI makes no network calls.

◆ Interview Q

"Walk me through what happens to one proxied request."

Use the 8-step list above out loud. The two things to emphasize: rate-limit/quota happen before the upstream call (so we don't waste an upstream request on a call we'll reject), and the log + usage + telemetry writes happen in the same DB transaction as each other so they're atomic.

◆ Interview Q

"If a quota check passes but the upstream call then fails, what happens to the counter?"

We roll back the consumed quota units for a request we never actually served upstream — the quota enforcer has a rollback that decrements the Redis counter. So a dead upstream doesn't silently burn a customer's quota.

08 · The interesting algorithm

Rate limiting

Three pluggable strategies (Strategy pattern), each backed by an atomic Redis Lua script. A rule is attached per API; the limit is keyed per (api, api_key) so one noisy consumer can't starve the others.

StrategyMechanismTrade-off
Fixed windowINCR a per-window counter with a TTL.Cheapest; but allows a 2× burst across a window boundary.
Sliding window (log)A sorted set of request timestamps; drop old, count, add.Accurate to the second; more memory per key.
Token bucketTokens refill at a steady rate up to a burst capacity.Smooth rate and a controlled burst; the most flexible.

▸ Why Lua? — the single most important point here

Rate limiting is a read-modify-write: read the counter, decide, update it. If two requests do that concurrently, they can both read "9 of 10" and both proceed — a race that lets you exceed the limit. Redis runs a Lua script atomically (single-threaded, no interleaving), so the check-and-increment is one indivisible operation. That's the whole reason the logic is in Lua and not in Python.

Each script returns {allowed, remaining, retry_after_ms}; on rejection the gateway raises a 429 carrying Retry-After, and successful responses get X-RateLimit-Limit / -Remaining headers.

◆ Interview Q

"Fixed vs sliding window — when does it matter?"

Fixed window resets the counter on a hard boundary, so a client can send the full limit at 0:59 and again at 1:00 — a 2× burst in two seconds. Sliding window looks at a rolling trailing window, so that burst is caught. Fixed is fine when approximate limiting is acceptable and you want minimal cost; sliding when the limit is a hard SLA. Token bucket is the middle ground: steady average with a bounded burst.

◆ Interview Q

"Why key the limit per API key instead of per API?"

Fairness. A per-API global limit means one heavy consumer can consume the whole budget and starve everyone else on that API. Per-key isolates tenants from each other. (A per-API ceiling could be layered on top if you also wanted to protect the upstream itself.)

09 · Longer-horizon limits

Quotas

Where rate limits protect against bursts (per second/minute), quotas cap total volume over a calendar period — daily or monthly. They're enforced with Redis counters keyed by {api_key}:{period}:{bucket}, where the bucket is the current day (2026-08-10) or month, with a TTL set to the end of that period so the key expires naturally.

Enforcement is a single atomic INCR; if it pushes over the cap we rollback (decrement) and reject with a quota_exceeded 429. The authoritative history still lives in request_logs / api_key_usage — Redis is the fast enforcement layer, Postgres is the source of truth.

◆ Interview Q

"Rate limit and quota both return 429 — why two mechanisms?"

Different time horizons and intents. Rate limiting smooths short-term load to protect the upstream and ensure fairness (requests/second). Quota enforces a commercial/plan limit over a billing period (requests/month). You want both: a customer can be under their monthly quota but still hammering you this second.

10 · The distributed-systems set-piece

Telemetry & the transactional outbox

This is the part that signals "I understand distributed systems." The problem: when the gateway serves a request, it must both write the request log to Postgres and publish a telemetry event for the downstream observability product. If you do those as two independent operations, you have the classic dual-write problem:

Naïve dual write:
   write DB  ✓ ───→ publish event  ✗ (broker down)   ⇒ event lost
   publish event ✓ ───→ write DB  ✗ (crash)          ⇒ event phantom (never happened)

The fix: transactional outbox

Instead of publishing directly, the request handler writes the event into an telemetry_outbox table in the very same DB transaction as the business write. Since it's one ACID commit, the event and the log are saved together or not at all — never lost, never phantom. A separate background worker then drains the outbox and delivers events to the real transport.

   ┌─ same transaction ─────────────┐
   │  INSERT request_log            │
   │  INSERT api_key_usage          │  ← all commit atomically
   │  INSERT telemetry_outbox (row) │
   └────────────────────────────────┘
                 │
                 ▼  (async, every ~10s — Celery beat)
        publisher drains pending rows  ──→  sink  ──→  Project B
        FOR UPDATE SKIP LOCKED · stamps published_at

Why FOR UPDATE SKIP LOCKED

So you can run multiple publisher workers safely. Each grabs a batch of pending rows and locks them; SKIP LOCKED means a second worker just skips the locked rows and takes different ones — no double-delivery, no contention. Rows are stamped published_at after delivery (kept, not deleted, so history survives).

Transport-agnostic by design (and no Kafka)

Delivery goes through a TelemetrySink interface. Today the sink logs structured events. Swapping in Kafka or Redis Streams later is a new sink class — zero change to the event schema, the outbox, or any business code. That's a deliberate call: Project A doesn't need a message broker's operational weight, so it doesn't have one, but nothing about the design blocks adding one.

The versioned contract

Events (request_log, audit_log) are Pydantic models carrying a schema_version. JSON Schemas are generated from them into telemetry/schemas/. The rule: additive optional fields don't bump the version; a breaking change does, and consumers must tolerate unknown fields. This is the contract the observability product consumes.

Audit logs use the same machinery: security-sensitive actions (key create/revoke/rotate) write an audit_logs row plus an outbox event, atomically.

◆ Interview Q

"How do you guarantee a telemetry event is never lost?"

Transactional outbox. The event row is written in the same DB transaction as the business change, so they commit together atomically — there's no window where one exists without the other. A background publisher delivers from the outbox and marks rows published; if delivery fails, the row stays pending and is retried. Delivery is therefore at-least-once, and consumers dedupe on the event's UUID.

◆ Interview Q

"Is delivery exactly-once?"

Exactly-once at the source (the outbox write is atomic with the business write). End-to-end delivery is at-least-once — a publisher could deliver a batch then crash before stamping published_at, re-delivering on restart. That's why every event carries a stable event_id for the consumer to dedupe. Trying to make it truly exactly-once end-to-end is famously not worth it; at-least-once + idempotent consumers is the standard.

11 · Read models

Analytics

Two-tier, because "raw" and "aggregated" queries have different shapes:

  • Live queries (summary, top endpoints, status breakdown) read request_logs directly, fast via the (api_id, created_at) index. p95 latency uses Postgres percentile_cont(0.95) WITHIN GROUP.
  • Time series reads a pre-aggregated daily_usage rollup, so a 90-day chart never scans the raw log table.

The rollup is rebuilt by a Celery job and is idempotent: it DELETEs the target day then re-INSERTs from the raw logs. Running it twice yields the same result — which matters because the "today" bucket is recomputed every 15 minutes as new traffic arrives.

◆ Interview Q

"Why pre-aggregate instead of just querying the logs?"

Scan cost. A dashboard showing 90 days of daily totals over a table with millions of rows would be slow and would hammer the same table the write path uses. The daily rollup turns that into a tiny indexed read. It's the read-model / CQRS idea: optimize the write table for writes, and maintain a separate shape optimized for the read.

◆ Interview Q

"Why does the rollup delete-then-insert instead of upsert-increment?"

Idempotency. Incrementing means running the job twice double-counts. Delete-then-recompute-from-source means the job is a pure function of the raw data — safe to re-run, safe to backfill, safe to run on a partial (still-open) day.

12 · The plumbing

Cross-cutting concerns

Configuration — 12-factor

All config comes from the environment via a typed, validated pydantic-settings object, loaded once and injected. No module reads os.environ directly. Secrets never ship in code; there are .env.example and production.env.example templates.

Error handling — one envelope

Domain code raises typed AppError subclasses (NotFoundError, PermissionDeniedError, RateLimitedError…). Central handlers render every error as {"error": {code, message, details, request_id}}. Stack traces are never exposed (OWASP); an unexpected exception becomes a generic 500 with the detail logged server-side.

Logging — structured & correlated

structlog emits JSON in prod. Every log line in a request carries its request_id/correlation_id (bound via contextvars in middleware), and the correlation id honors an inbound header so a trace can span services — the first hook the observability product uses.

Migrations — Alembic, async, verified

Schema changes are Alembic migrations autogenerated against a real Postgres, and every migration is verified with an upgrade → downgrade → upgrade roundtrip before it lands. The env runs async against the same engine as the app (one source of truth for the DB URL).

Observability hooks

/health/live + /health/ready (checks DB + Redis) for probes, a Prometheus /metrics endpoint, and OpenTelemetry API/SDK wired as no-op hooks ready for a real exporter.

13 · Confidence

Testing strategy

90 tests, 85% coverage, run every milestone (not deferred to the end). The pyramid:

  • Unit — pure logic (security primitives, permission catalog, config parsing) with no external deps. Fast, no Docker.
  • Integration / API — the app driven by an httpx AsyncClient against real Postgres + Redis via Testcontainers. Real DB, real Redis, real SQL — not mocks.

The gateway's outbound upstream call is the one thing mocked (with respx), so tests are deterministic and CI never touches the network — while the real upstream integration stays available for manual demos.

▸ Why Testcontainers instead of SQLite or mocks?

Because the code uses Postgres-specific features — percentile_cont, ON CONFLICT upserts, JSONB, FOR UPDATE SKIP LOCKED. SQLite would pass tests that break in prod. Testcontainers spins up the real Postgres 16 in a throwaway container, so the tests exercise exactly what production runs.

◆ Interview Q

"How do you test rate limiting or the outbox without flaky timing?"

Rate limiting runs against a real Redis (Testcontainers) and asserts the Nth request flips to 429 — deterministic because the Lua script is deterministic. The outbox test drives a real gateway call, asserts a pending row exists, runs the drain function, and asserts it's marked published. No sleeps, no wall-clock races.

14 · Shipping

Deployment & ops

  • Multi-stage Dockerfile: deps built into a venv in a builder stage, copied into a slim runtime image that runs as a non-root user with a HEALTHCHECK.
  • docker-compose brings up the whole stack: Postgres, Redis, the API (runs alembic upgrade then serves), a Celery worker, a Celery beat scheduler, and the nginx-served frontend.
  • CI (GitHub Actions): ruff (lint + format), mypy, the full pytest suite (the runner's Docker daemon backs Testcontainers), frontend type-check + build, and a Docker image build.
  • The frontend is a minimal React + TS + Vite + Tailwind + React Query dashboard, served by nginx which proxies /api to the backend.

Verified end-to-end live: compose up → healthy → a real request proxied to httpbin.org → the worker drained the telemetry outbox → the dashboard rendered the live numbers.

15 · The senior questions

Scaling & trade-offs

Interviewers push on "what breaks at 100×?". Honest answers:

◆ Interview Q

"How does this scale horizontally?"

The API is stateless (access tokens are stateless; all shared state is in Postgres/Redis), so you run N replicas behind a load balancer. Rate limiting and quotas are already in Redis, so they're correct across replicas. The outbox publisher scales out too — SKIP LOCKED lets multiple workers drain concurrently. The bottleneck becomes Postgres.

◆ Interview Q

"request_logs will get huge. What then?"

It's already decoupled and indexed on (scope, created_at) for exactly this. Next steps: partition by time (monthly partitions, drop old ones cheaply), move raw logs to a column store (ClickHouse/Timescale) for analytics, and rely on the daily_usage rollup so dashboards never touch raw rows. The write path already goes through the outbox, so shipping logs to a separate store is a sink change, not a rewrite.

◆ Interview Q

"What are the current limitations you'd fix first?"

Be honest — it reads as senior: (1) rejected gateway requests (429/401) aren't persisted as request_logs, only access-logged; (2) quota counters live only in Redis, so a flush resets in-flight windows; (3) the outbox publisher polls every 10s — fine now, but I'd move to a push/stream for lower latency at scale; (4) rate limiting is per-key only — I'd add an optional per-API ceiling to protect upstreams.

◆ Interview Q

"Single Redis is a SPOF for the gateway. Thoughts?"

Correct. In production I'd run Redis in a replicated/clustered mode. There's also a design choice about failure mode: if Redis is down, do you fail open (allow traffic, lose limiting) or fail closed (reject)? For a rate limiter, fail-open is usually right — you'd rather serve traffic than take an outage — with alerting so it's not silent.

16 · "Tell me about a hard bug"

War stories — real bugs from the build

These are gold when asked about debugging. Each is a real issue that came up and how it was diagnosed.

⚠ asyncpg "attached to a different loop"

Integration tests failed intermittently in the DB health check. Cause: a session-scoped async engine — asyncpg connection pools are bound to the event loop that created them, but pytest-asyncio gives each test its own loop. Fix: make the engine function-scoped (one per test, bound to that test's loop); keep the expensive containers session-scoped. Lesson: async resources are loop-affine.

⚠ MissingGreenlet during RBAC seeding

Reassigning a lazy-loaded relationship (role.permissions = [...]) triggered a synchronous lazy-load inside an async context → MissingGreenlet. Fix: await-load the collection first via SQLAlchemy's awaitable_attrs (which required adding the AsyncAttrs mixin to the base). Lesson: in async SQLAlchemy, implicit lazy I/O is a trap — load explicitly.

⚠ Empty schema in tests

create_all() silently created nothing on some runs. Cause: the models package wasn't imported before Base.metadata was read, so the metadata was empty — it only "worked" by collection-order luck. Fix: an explicit import app.models in conftest. Lesson: ORM table registration is an import side effect; make it deterministic.

⚠ Postgres round(double, int) doesn't exist

An analytics query threw a ProgrammingError — Postgres has round(numeric, int) but not round(double precision, int). Also hit a subtle one: labeling a column count collided with Python's tuple .count method on the result row. Fixes: round in Python, and never label a column with a tuple method name. Lesson: the DB's type system and the driver's row API both have sharp edges.

⚠ Deployment: three container gotchas

(1) The Docker build failed because pyproject.toml referenced a README outside the build context → dropped the reference. (2) Celery beat crashed with "permission denied" writing its schedule file — the container runs non-root and /app isn't writable → pointed --schedule at /tmp. (3) The frontend nginx returned 502 after I rebuilt only the API container — nginx had cached the old container's IP → restart re-resolves. Lesson: non-root containers and DNS caching bite in the last mile.

⚠ List env var wouldn't parse in Docker

CORS_ORIGINS=http://localhost:5173 crashed startup — pydantic-settings tries to JSON-decode list-typed fields from env before a validator runs. Fix: annotate the field with NoDecode and split the string myself. Lesson: settings libraries have opinions about complex types from env strings.
